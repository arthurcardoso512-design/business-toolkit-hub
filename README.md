MICRO-SAAS — HUB DE FERRAMENTAS PARA PEQUENOS NEGÓCIOS

1. PAPEL E OBJETIVO

Você é um engenheiro de software sênior, arquiteto de sistemas, especialista em SaaS, UX/UI e desenvolvimento full-stack.

Você está construindo um Micro-SaaS real para pequenos negócios.

O produto será um HUB de ferramentas profissionais simples, rápidas e fáceis de usar.

O objetivo não é criar um site com vários "geradores".

O objetivo é criar uma plataforma SaaS completa, com:

- cadastro e login;
- conta de empresa;
- ferramentas gratuitas;
- ferramentas Premium;
- controle de acesso;
- banco de dados;
- armazenamento;
- pagamentos;
- controle de validade do Premium;
- integração com Asaas;
- Pix;
- Webhooks;
- dashboard;
- área do cliente;
- área administrativa;
- segurança;
- responsividade;
- tratamento de erros;
- arquitetura preparada para crescimento.

IMPORTANTE:

Não implemente soluções falsas, simuladas ou apenas visuais.

Tudo que estiver disponível para o usuário deve funcionar de verdade.

Se alguma integração externa ainda não estiver configurada, crie a arquitetura correta para recebê-la e deixe claramente identificado o que depende das credenciais externas.

Não invente APIs, endpoints, chaves ou respostas de serviços externos.

Nome provisório:

HUB

O produto será uma plataforma onde pequenos negócios podem encontrar ferramentas para:

- divulgar;
- atender;
- compartilhar informações;
- receber pagamentos;
- criar materiais;

- facilitar tarefas do dia a dia.

Posicionamento:

"Seu negócio. Suas ferramentas. Um só lugar."

A comunicação deve ser simples.

Evitar linguagem técnica desnecessária.

O sistema deve sempre explicar:

1. O que a ferramenta faz.

4. O que é gratuito.

28. SEGURANÇA DO BANCO

Implementar Row Level Security.

Um usuário:

só pode visualizar seus próprios dados;

só pode editar seus próprios recursos;

não pode acessar pagamentos de outro usuário;

não pode acessar documentos de outro usuário;

não pode alterar manualmente seu próprio status Premium.

Status Premium não deve ser controlado somente pelo frontend.

35. IDEMPOTÊNCIA

O webhook deve ser idempotente.

Se o mesmo evento for recebido duas vezes:

não duplicar o período Premium.

Registrar eventos processados ou utilizar identificador único do evento/pagamento.

Exemplo:

Pagamento:

R$ 19,90

Evento recebido duas vezes.

Resultado:

+30 dias apenas uma vez.
